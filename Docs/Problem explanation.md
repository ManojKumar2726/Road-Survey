# How is Edge Computing Achieved?

The key idea is to **perform perception on the bus itself and transmit only structured observations**, rather than continuously transmitting raw camera footage to a central server.

### 1. Multi-task perception at the edge

Instead of running several heavy specialized models independently:

```text
Video
  ↓
Pothole model
Vehicle model
Pedestrian model
Sign model
...
```

use a **single multi-class detector** on the onboard system.

The model can detect multiple classes simultaneously:

```text
                Multi-class detector
                       ↓
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
    Vehicles       Pedestrians     Road damage
        ↓              ↓              ↓
   count/speed      tracking       severity
```

The raw detection output can then be converted into **different event formats depending on the detected class**.

For example:

* Vehicle → count, class, speed
* Pothole → location, confidence, severity
* Pedestrian → position, tracking information
* License plate → plate number + confidence

This avoids maintaining a separate inference pipeline for every individual urban problem.

---

# Accuracy vs. Edge Efficiency

A single multi-class model may be **less accurate for a particular task** than a highly specialized model trained specifically for that task.

Rather than treating this as a problem, the system can use a **priority hierarchy**.

### Higher-priority detections

These should receive greater emphasis in model training/inference:

1. **Pedestrian safety**
2. **Hit-and-run / dangerous driving**
3. **Traffic incidents**
4. **Vehicle/traffic detection**

### Lower-priority detections

These can tolerate lower individual detection accuracy:

5. **Potholes / road damage**
6. **Missing dividers**
7. **Road markings**
8. **Other infrastructure defects**

The important idea is that **the same observation can be made repeatedly by multiple buses**.

For example:

```text
Bus 01 ──┐
Bus 07 ──┤
Bus 14 ──┼──→ Same pothole
Bus 23 ──┤
Bus 31 ──┘
```

A single imperfect detection does not necessarily become the final conclusion.

Repeated observations from different buses can increase confidence that a problem actually exists.

> **Fleet redundancy can therefore compensate, to some extent, for imperfect individual observations.**

I'd use **"to some extent"** here rather than saying accuracy is not important. Safety-critical detections still need high reliability.

---

# 2. Reduce the inference workload

The camera may capture at **30 FPS**, but most urban infrastructure does not need to be analyzed at 30 FPS.

Therefore:

```text
30 FPS camera
      ↓
Frame sampling
      ↓
5 FPS / 10 FPS
      ↓
AI inference
```

The exact sampling rate can be adjusted depending on the detection task.

This significantly reduces:

* CPU/GPU utilization
* power consumption
* thermal load
* inference cost

while still providing sufficient temporal coverage for relatively slow-changing road conditions.

---

# 3. Edge generates observations, Central system generates intelligence

This is an important architectural separation.

### On the bus — **Perception**

The edge system answers:

> **"What is happening in front of this bus?"**

```text
Camera
  ↓
AI model
  ↓
Detection
  ↓
GPS + timestamp
Bus ID + route ID
Confidence + severity
Evidence
  ↓
Structured event
```

Only this compact information needs to be transmitted.

### Central platform — **Intelligence**

The central system answers:

> **"What is happening across the city?"**

```text
Observations from
many buses
       ↓
Central database
       ↓
Aggregation
Deduplication
Temporal analysis
Spatial analysis
       ↓
GIS + Analytics
```

This is where you perform:

* congestion heat maps
* repeated road-defect identification
* fleet-wide traffic analysis
* infrastructure deficiency analysis
* route delays
* historical trends

# The Overall Edge Strategy

You can put all of this into **one slide**:

### **Edge AI Strategy**

> **Run lightweight, multi-task perception on each bus and transmit only structured observations to the central platform.**

| Strategy                            | Purpose                                                                             |
| ----------------------------------- | ----------------------------------------------------------------------------------- |
| **Single multi-class detector**     | Detect multiple urban objects/problems in one inference pipeline                    |
| **Task-specific output processing** | Convert different detections into appropriate event formats                         |
| **Priority hierarchy**              | Allocate greater emphasis to safety-critical detections                             |
| **Frame sampling**                  | Reduce 30 FPS video to a lower inference rate                                       |
| **Fleet redundancy**                | Repeated observations from multiple buses improve confidence in persistent problems |
| **Edge perception**                 | Generate detections locally without continuously transmitting raw video             |
| **Central analytics**               | Perform aggregation, correlation, heat maps and city-level intelligence centrally   |

### The novelty angle

I would **not** claim:

> "Our novelty is running multiple detection models simultaneously."

That's technically weak because multi-model/multi-task inference already exists.

Instead, pitch the novelty as:

> **"A fleet-scale edge perception architecture that uses a unified multi-class detector and task-specific event extraction to convert existing public-transport cameras into distributed urban sensors, while shifting computationally intensive city-level analytics to a centralized platform."**

And your particularly interesting design insight is:

> **The buses don't need to independently produce perfect knowledge of the city. They act as distributed, redundant observers whose individual observations can be combined centrally to produce more reliable urban intelligence.**

That is a much stronger story for the PBL problem statement.
